# 01 · 项目架构设计说明书

> 项目：environmental-monitoring（drenep）｜四端环境监测与监督系统
> 本文档基于真实代码扫描生成（工程文档阶段），不包含虚构内容。

## 1. 项目背景

面向校园/园区/城区的环境质量监测与公众监督需求，覆盖空气（PM2.5/CO2/温湿度）、水质（pH/浊度/溶解氧）、噪声三类指标，以及“公众发现环境问题 → 网格员现场检测 → 管理员处置”的监督业务闭环。

## 2. 项目目标

- 环境数据自动采集、实时展示、阈值告警闭环（原有 NEPV 体系）
- 四端协同：公众监督（NEPS）→ 审核派单（NEPM）→ 现场检测（NEPG）→ 决策可视化（NEPV）
- 一套后端 + 一套数据库支撑四端，业务数据（事件/任务/检测/日志）跨端真实流动

## 4. 四端架构

| 端 | 定位 | 身份/登录 | 核心页面 | 差异化视觉 |
|---|---|---|---|---|
| **NEPS** | 公众环境监督服务 | users 表（zhang_san 等）`/auth/login-public` | 首页/我要监督/我的监督/详情/消息 | 亲和绿 · 移动端优先 · 大圆角 |
| **NEPM** | 环境监管业务管理平台 | admins 表 `/auth/login` | 工作台/监督事件/网格/网格员/任务 | 专业蓝 · 侧边栏 · 高密度表格 |
| **NEPG** | AQI 检测网格员工作端 | users 表（王强等）`/auth/login-public` | 我的任务/任务详情/检测表单/历史 | 任务橙 · 移动端优先 · 任务卡片 |
| **NEPV** | 决策可视化驾驶舱 | admins 表 `/auth/login` | Dashboard 大屏/空间态势/历史/设备/告警/阈值/用户 | 绿色驾驶舱（保持原设计） |

四端共享：同一后端 API、同一 MySQL、同一设计令牌（tokens.css）基座；按角色差异化主题色/布局（app-theme.css）。

## 5. 前端架构

- 技术：Vue 3.5 + Vite 5 + Pinia + Vue Router 4 + Element Plus 2.8 + Axios + ECharts 5
- 统一模式：`src/api/index.js`（全部接口封装）→ `utils/request.js`（axios 拦截：token 注入、{code,message,data} 解包、401 跳登录）→ `utils/ws.js`（/ws/notify 身份连接 + 3s 重连）→ `store/`（会话 localStorage，key 四端隔离）
- 身份传递：请求头 `X-User-Id`（公众/网格员）、`X-Admin-Id`（管理员）+ `Authorization: Bearer <token>`
- 路由守卫：无 token 跳登录；各端登录态隔离

## 6. 后端架构

- 技术：Spring Boot 2.6.13 / Java 8 目标（JDK 21 运行）/ MyBatis-Plus 3.4.1 / MySQL 8
- 分层：`ctrl`（16 个 API Controller）→ `service`+impl（12 组）→ `dao`（17 BaseMapper）→ MySQL
- 支撑：`common`（Result/PageResult/GlobalExceptionHandler）、`exception`（BizException）、`config`、`ws`、`dto`（17）、`bean`（17 实体）
- 业务域：认证（admin/users 双通道）、监督事件（附件/状态日志）、网格与网格员、巡检任务（检测记录/AQI 计算）、监测数据（上报/阈值/告警/质量/异常/健康度）、统计

## 7. 数据库架构

MySQL 库 `nep`（utf8mb4/InnoDB），17 表：认证（admins/users）、基础（regions/devices/sensors）、监测（monitor_data/alerts/thresholds/data_quality）、监督业务（supervision_event/supervision_attachment/event_status_log/event_evaluation）、网格任务（grids/grid_member/inspection_task/inspection_record）。详见《02-数据库设计说明书》。

## 8. API 架构

- 统一前缀 `/api`，统一响应 `{code, message, data}`（200 成功；400 参数；401 未认证；403 无权限；500 异常）
- 分组：`/api/auth`、`/api/supervision`、`/api/tasks`、`/api/grids`、`/api/grid-members`、`/api/devices|data|alerts|thresholds|sensors|stats|situation|health|quality|anomalies|users`
- 身份来源：请求头 X-User-Id / X-Admin-Id（Service 层校验归属与有效性）
- 详见《03-接口文档》与 `docs/api/` 四端清单（全部来自真实 Controller 扫描）

## 9. WebSocket 架构

单端点 `/ws/notify`（Spring 原生 WS，非 STOMP）：
- 连接身份：query `role=ADMIN|GRID|PUBLIC&id=xxx`
- 全量广播 `broadcast()`：data/alert（NEPV 实时数据与告警，向后兼容）
- 定向通知：`sendNotifyToAdmins` / `sendNotifyToUser`（SUPERVISION_CREATED/TASK_ASSIGNED/TASK_ACCEPTED/DETECT_SUBMITTED/EVENT_CLOSED）
- 原则：WebSocket 只做实时提醒；数据一律以 REST API + MySQL 为准

## 10. 权限架构

- 管理员（admins 表）：全部管理接口（审核/派单/核实/关闭、网格、网格员、任务、用户、告警）
- 公众（users + X-User-Id）：创建/查看本人事件 + 公开只读数据
- 网格员（users + X-User-Id + 任务归属）：仅本人任务（接收/开始/提交检测）
- 数据级隔离：事件按 user_id、任务按 assignee_id 归属校验（越权 401/403）
- 说明：users.role 为语义标记；鉴权基于身份头+归属校验+admins 表（token 不校验见《07》BUG-003）

## 11. 数据流

```text
采集：模拟器(5s/轮, 场景引擎) 或 硬件POST /api/data/report
      → monitor_data + 设备在线 + 阈值告警(alerts) + WebSocket(data/alert)
监督：NEPS提交 → supervision_event(PENDING_REVIEW) → WS通知管理员
      → NEPM审核(APPROVED/REJECTED) → 派单 → inspection_task + WS通知网格员
      → NEPG 接单/开始/检测 → inspection_record(六项+AQI) → WS通知管理员
      → NEPM 核实(VERIFIED)/关闭(CLOSED) → WS通知公众
统计：NEPV GET /stats/overview|supervision（业务表实时聚合）
```

## 12. 业务流（完整闭环）

公众提交 →（PENDING_REVIEW）→ 管理员审核 →（APPROVED）→ 派单 →（ASSIGNED，创建任务）→ 网格员接单 →（ACCEPTED）→ 开始 →（INSPECTING）→ 现场检测（六项→AQI）→（INSPECTED）→ 管理员核实 →（VERIFIED）→ 关闭 →（CLOSED）→ 公众查看“已处理”；每次状态变化写 event_status_log（8 条时间线）。详见《04》。

## 16. 架构设计原则

1. 前后端分离 + 分层；Controller 不直连 DAO（业务域自监督模块起落实）
2. 状态机收敛于 Service；前端不可传 status（DTO 无 status + Service 强设）
3. 数据库最小迁移：只增表/增可空列，禁止删改现有结构与数据
4. 单一 WebSocket 端点 + 定向通知；通知不替代数据库
5. 兼容优先：NEPV 既有接口/广播零破坏；新功能一律新增端点
6. 真实数据：无前端 Mock；统计全部来自业务表（模拟器仅用于监测数据采集演示）
